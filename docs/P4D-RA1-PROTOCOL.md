## 1. Boundary and compatibility

RA1 is an internal authority extension for the synthetic reference application, not a selected host/SDK/model/provider transport, production deployment/storage decision or live API permission. New runtime code and actual I01–I05 integration are **NOT IMPLEMENTED / NOT RUN** here. No DB/WSL/container/QA/native/provider execution, real account/key/project, install, pilot/publish or Git mutation. Reading official documentation and evaluating authored data with existing pure functions are design checks only.

Public mutation bodies and the frozen HTTPS route allowlist remain `m50-application-1.1.0`. RA1 adds a separately authenticated **private** `dispatch_authority(context, request)` contract `ra1-authority-1.0.0`; no `/v1/reasoning_*` route is silently added to the frozen transport. RA1-owned reports/source/export require the explicitly opt-in read profile in §7a; legacy reads fail E_VERSION after authorization rather than mislabel imported data as executed. The [authority request schema](../schemas/ra1-authority-request-v1.schema.json) and [read request schema](../schemas/ra1-read-request-v1.schema.json) are shape/wire design, not authentication or callable endpoints. Runtime implementation must separately enforce current DB policy/time/identity, immutable registry references and transaction predicates below.

There is one application/core/report lifecycle. RA1 may normalize and privately stage a candidate; only existing `assessment_accept` under the assessor audience accepts it, and only assigned `worker_submit` publishes via the unchanged core/publication rules. JSON-valid output, mapper success, gateway credentials, fixture enrollment or `ok=true` never supplies accepted QA facts, cleanup truth or human approval.

`valid_config` still enforces `outboundProviders == []`. RA1 policy has **mode=authored_fixture, network=disabled**. It may further restrict configured source scope and approved fixture ports, never permit a real outbound call or override base data policy. Supplemental tables live inside the same authority transaction domain, not an alternate permission service. Actual external/local-host readiness needs a later authorized profile with enforceable context/tools/outbound, usage and secret custody.

Do not alter old runtime_candidate, RC1, identity, fixtures or manifests to simulate new compatibility. ## 3. Records and trusted ownership

All mutable RA1 records serialize under the existing identity `control FOR UPDATE` mutex used by user/service/config/grant changes. Unique/FK/CAS constraints add defense; a process-local lock does not substitute for this ordering. Store.unit end predicates use DB `clock_timestamp()`, not request/client time or transaction-start `now()`.

Role separation is enforced by actual credentials and stored identity/scope, not body assertions. An Admin may enroll/revoke dummy gateways privately; Owner/Admin may set a further-restricting policy within an enabled project. No project role can read secret/raw quarantine merely because it can configure policy. One service credential cannot be interchangeable across the four existing audiences or gateway audience.

### Stored phase is not a cancellation or accounting witness

Stored phases are `admitted`, `release_claimed`, `candidate_ready`, `accounting_unresolved`, `refused`, `incomplete`, `malformed`, `unsupported`, `provider_error`, `unresolved_send`, `accepted`, `published`. Admission/reservation is one atomic transition; release_claimed consumes its unique claim; one response determines candidate/failure state; assessment_accept alone may advance candidate_ready→accepted; worker_submit alone accepted→published. Late accounting, ordinary read, cancellation, expiry or metadata replay never advances a failure/unknown state to candidate_ready/accepted/published. No transition returns to admitted or permits a second release. Original normalized observations and accepted/published receipts are immutable.

Independent fields are `intentOpen`, `accountingStatus=pending|reconciled|incident`, current `fences={cancelled,expired,authorityCurrent}` and the monotonically increasing attempt version. Fences determine admission/acceptance/publication eligibility without overwriting failure phase, closing uncertainty or reclassifying already published history. Safe reasoning_read includes these fields; read authorization is per audience: current users with project read scope may see this bounded diagnostic history even if gateway is disabled, while gateway/assessor/worker private content/receipt operations additionally require their pinned current service and RA-policy authority. Such a diagnostic is never a resumable capability.

## 4. Private operations, responses and errors

Request shape: exact `{version,operation,params}`. Schema version is `ra1-authority-1.0.0`, finite canonical UTF-8 JSON ≤64KiB; duplicate keys/nonfinite/invalid UTF-8 reject. IDs follow current identifier grammar; UUID-like assignment/effect refs stay 32 lowercase hex; SHA256 64 lowercase hex. Runtime strict integer fields exclude bool **and** floating representations such as 1.0 even where JSON Schema's mathematical integer type accepts them. Policy port IDs must be unique even when two same-port objects differ in selector fields; JSON Schema uniqueItems alone is insufficient. Unknown fields/versions/operations reject, no dynamic dispatch name from data.

Credential and receiver context are authenticated out of band. New gateway operations use exactly one `Store.unit(token=None, write=...)`, then authenticate the `g.` digest/epoch/project/expiry inside that unit and append expiry to its deadline list. Passing an `s.`/`a.` token as gateway, missing/revoked/expired gateway or cross-project credential denies. Admin/Owner operations use the existing user-token unit/role checks. Never call `Store.unit(kind='gateway')` on the frozen four-audience implementation or insert an unsupported kind into rt_services.

All successful private responses have exact envelope `{version,operation,ok:true,result}` with the per-op fields above. gateway_enroll's credential and reasoning_candidate_read's exact assessment packet are confidential private-channel data, not safe metadata. Errors are exact `{version,operation,ok:false,error:{code}}`; codes use existing `E_INPUT,E_VERSION,E_AUTH,E_DENIED,E_CONFLICT,E_STALE,E_BUDGET,E_UNRESOLVED,E_INTEGRITY,E_DEPENDENCY`. No path/token/raw body/traceback/message echo. Unknown operation uses `operation:null` in error, never reflects arbitrary text. Transport HTTP status mappings remain irrelevant for this private function contract; no new public endpoint is implied.

`key` is idempotency only, not authority. For operations with a key, receipt uniqueness is `(actor audience,actor ID,epoch,project,key)`, with **operation and canonical request digest stored as immutable values**. Reuse across operation/body/fixture/owner conflicts under the same mutex, rather than an operation-inclusive PK accidentally allowing it. Exact committed retries reauthorize current read authority and return prior safe receipt without new reservation/send/core evaluation/refund/assessment/report/event. For mutation retry with mismatched expected version, exact original key/body receipt wins only as historical metadata; a new key does not recreate work. No automatic retries, implicit SDK continuation, corrective resubmission, port/model fallback or budget expansion.

## 5. Release, receipt, accounting and cancellation

Admission freezes actual current run/snapshot/assignment/fence/effect and collector record. It requires run phase awaiting_assessment, current `Store.current_work` delegation, enabled exact base+RA policy, gateway/worker credentials, explicit lineage permission, known source/contract/model/route pins and sufficient vector capacity. The immutable attempt ID→offer digest check precedes allocation; funded different-attempt races still cannot create a second run binding. Shape/policy/capability/budget rejection before intent has no new release/reservation/run/report effects.

Admission itself binds the actual live server-owned receiver context, before any release claim. The release claim is another single write transaction, committed **before** context leaves the server; it must match that original volatile owner/generation, not just the same gateway credential and CAS number. No operation can rebind it. A trusted handle is issued once for that driver; receiver IDs/generations are not caller fields and cannot be reconstructed from DB metadata. A fresh process after admitted-intent orphaning cannot claim even when release_claim never occurred, expected_version matches and budget remains. Proven never-admitted work may be admitted by a fresh authorized owner; committed intent cannot. Lost/ambiguous delivery gives metadata replay only, never regenerated owner/handle. Claim response loss, crash before first byte or partial request retains intentOpen/reservation; no resend/resume/new attempt, even without a provider request ID. No exactly-once remote execution guarantee.

Only the registered offline sink receives bytes; no arbitrary callback/socket/process tool exists in RA1. An internal release iterator holds the per-live-handle serialization guard and checks the current DB/identity mutex through **each actual copy of at most4096 bytes**, total encoded context ≤64KiB. It rechecks gateway/receiver owner, current user/project/grant/config/RA-policy/capability, assignment/fence/lease/run/attempt deadlines and exact request bytes before each copy. Previously admitted bytes are irreversible; revocation committed before the next admission stops that chunk. No lock is held through model computation. A consumed handle cannot restart at offset0; no durable byte-progress counter is permission to resume after loss. Ordinary readside.release_unit is not reused as a reasoning gateway.

The fixed trusted sink must accept exactly one **complete framed request** before admitting its one fixture invocation. It accumulates actual accepted bytes without invoking on prefixes; checks exact framing, actual byte count and SHA256 against the pinned request plus route/model/enrollment/offer/owner-generation; rejects truncation, changed bytes, extra frame or iterator exception. Only after full validation does its private issuer create one nonreplayable receipt `{attempt,release,ownerGeneration,offerDigest,actualFrameBytes,actualFrameSha256,invocationId}` bound to that original live channel and exactly one admitted fixture invocation. Neither gateway body nor a preauthored response can mint it. Candidate-eligible receive observations require this stored receipt and matching invocation ID, as do candidate_read/assessment/publication guards. No positive receipt for zero/prefix copies, uncertain sink acceptance or failed iterator; even an otherwise valid prebound success on the SAME still-live channel then yields only noncandidate unresolved_send/incomplete or separate trustworthy accounting. Enrollment, expected hash, release_claimed and receiver ownership alone are insufficient. No receipt reconstruction/resume or second invocation after loss; crash/ambiguity retains intentOpen/reservation and denies candidate eligibility. This proves a bounded fixture sink admission only, not actual provider/model execution.

Cancellation remains existing `run_cancel`; because it uses the same identity mutex, it orders against new acceptance/publication. It does **not** have to edit intentOpen to block either guard. Remote/model termination is always unknown in this fixture profile, even if a local copy is fenced. A request may have released bytes before cancellation; do not claim they were recalled. `intentOpen` is independent of phase/cancel/expiry/failure and can close only on trustworthy one-shot completion/accounting, never by a boolean cancel/cleanup flag or a missing marker. No later run/attempt automatically takes its reservation.

One operator-enrolled delivery belongs to the exact offer/port/profile and actual original receive handle, with a candidate-eligible observation additionally tied to the actual full-frame sink receipt and its single invocation. Same-job sibling/policy/port bytes cannot be reattached; model echoes alone do not prove attempt identity. Legitimate identical bytes on a correctly bound fixture channel remain authored transport evidence. Missing/ambiguous channel stays unresolved. Store receipt hash, original delivery hash and request hash; replay checks these against private retained bytes without mapping/core work again.

Server normalization reuses three RC1 modules independently. Missing/wrong model echo is checked only for otherwise candidate-eligible success; HTTP429/timeout/refusal/incomplete keep their prior outcomes even without a model. Unknown/invalid/negative/bool counts retain reservation; candidate becomes accounting_unresolved, not accepted. Counts within independent bounds convert reservation to consumed + unused capacity exactly once; duplicate exact counts are no-ops, changed/over-bound counts create durable accounting incident and block new work. A noncandidate failure/refusal stays that failure even with a budget incident. Price/monetary cap is unknown, not inferred from token vectors.

`reasoning_account` is the separate legal late-count edge. The trusted original receiver creates immutable accounting observation IDs bound to attempt/offer/request/owner and observed final-usage source; an interim/missing/ambiguous usage event cannot close intentOpen. It may reconcile a previously unknown final vector exactly once under current gateway authority and CAS, even after local cancel/expiry, but never promotes an old receipt or returns a new release right. Initial/late counts use the same ledger reducer: exact two strict nonnegative integers within reservation convert reserved→consumed+unused; an already reconciled identical vector leaves balances unchanged; invalid/changed/over-bound observations set a durable account incident, preserve prior consumed/reserved amounts, and block fresh acceptance/publication. Preserve original refusal/error/cancel phase and prior report history. For a new contradictory observation, commit that incident **before** returning E_INTEGRITY/E_BUDGET outside the unit; do not raise inside and roll the incident back. Exact same key/body replay is read-only/no new witness; a distinct observation/key may add its own audit receipt without a second refund. Trusted accounting observations are registered under the same authority mutex before they become available to any operation; pending observations fence candidate acquisition/acceptance/publication until reduced. A stale expected_attempt_version never discards an already registered contradiction: under current gateway/original-channel authentication, consume such an observation into a durable authority-reducing incident, without refund/promotion, then return the safe error after commit. Ordinary valid reconciliation still requires CAS; a stale valid observation stays pending and blocks fresh work until an authorized CAS reduction. No caller may supply a pending/incident flag; both derive from server observations. If observation registration itself is uncertain, fence the live attempt before further candidate effects and retain uncertainty rather than admit success. This preserves any report committed before observation registration as historical, while a contradiction registered first blocks later publication. Lost owner/channel or revoked gateway cannot invent late proof/refund; reservation/incident remains pending maintenance outside RA1.

Observation after run cancel/expiry may update private history/accounting from the already bound live receiver when gateway credential is still current, but cannot become a candidate/assessment/report. If gateway credentials themselves are revoked or the receive handle is lost, this private request is denied and reservation stays open; later maintenance recovery is outside RA1. No invented refund or automatic repair. Terminal receipt/read replay uses current project/source/capability/identity **read** checks, not the expired historical attempt/run deadline; it never admits new work. All new acceptance/publication still require live work deadlines at final Store.unit commit.

## 6. Acceptance and publication guards

`candidate_ready` is private normalized/schema/core-valid data with reconciled within-bound usage and a positive actual-full-frame sink receipt/one-invocation binding; pending accounting observations fence acquisition, not accepted QA. Only the intended assessor receives the stored candidate via reasoning_candidate_read under current audience/project/source/policy/identity/attempt checks through each actual private release chunk. Its exact result is a full **existing assessment_accept body**; the assessor sends it using its own enrolled credential through normal Application.dispatch/TLS. Reading may repeat under fresh current authorization after a truncated private reply, but only reads immutable bytes, never invokes a mapper/core/model or changes budget. No bootstrap golden packet, direct DB handoff or gateway-submitted accepted digest is needed. After actual acceptance, the assigned worker acquires only the accepted assessment_digest via reasoning_worker_receipt and uses its own ordinary worker_submit lease body. Recheck all guards at the subsequent mutation; acquisition never grants authority that survives later revoke/cancel.

Assessment gate loads the exact original offer/observed response/projection from server blobs, requires the positive actual-full-frame sink receipt with matching one-invocation observation, no pending accounting observations/incidents, and compares incoming `bundle`, `assessment` and digests canonically to those candidate bytes, confirms independently accepted collector execution, current assessor+gateway+worker identity/epochs/delegation and all policy/fence/deadline pins. Then frozen `_collect_or_assess` runs and the RA1 acceptance linkage commits atomically with its assessment row/event. Worker/collector/gateway cannot act as assessor. Raw provider self-hashes or worker-supplied accepted labels cannot create this linkage.

Publication gate loads that accepted linkage and immutable blobs, checks worker identity/lease, same attempt/offer/response/assessment/execution, the same full-frame sink receipt/invocation, no pending accounting observation or open incident, no cancellation/expiry/current-authority loss, then calls frozen `_publish`. Report + completed + one report_ready and RA1 publication link share the **same** unit/one witness. Accepted assessment before a later revoke/cancel remains historical but cannot be published; no second report or relabeling. Both narrow branches append the minimum of gateway credential expiry, attempt deadline and existing run/lease/grant/service deadlines before expensive projection/blob/witness IO. Equal deadline is expired. A final predicate failure rolls SQL back; the existing external-witness mismatch protocol keeps uncertainty fail-closed, never guessed success.

Completed worker_submit exact replay is a separate guarded read case inside its one worker unit: confirm original assigned worker/lease digest and exact assessment/report link; reauthorize current gateway/service/owner/project/source/config/RA-policy/role epochs and nonrevocation, while not treating elapsed historical work deadlines as authority for new effects. No core/refund/publication/event is repeated. This does not grant ordinary content access; report/source/export use their existing current user authorization. Terminal history is immutable; later policy revocation denies new private read/ack when its current read predicates no longer hold.

Assessment response-loss replay has an equally explicit accepted-receipt branch **before phase/new-work checks**, including run analyzing or already completed. Compare canonical full original assessment request digest, assessor identity/epoch, assignment/fence/effect, candidate/config/authority and stored acceptance linkage, then return the prior safe receipt under current read authority, without prepare/core/blob writes or a new witness. Changed packet/digest/owner denies. Completed submit replay is also write=False. A preliminary read may race a first commit: recheck inside the later fresh write unit; if it discovers an already committed exact receipt, validate all current read predicates and last DB credential-expiry/witness checks, then use a private `ReplayOnly` sentinel **before any mutation** to unwind/roll back that read-only transaction before Store.unit's write-witness section. Catch it outside and return the receipt. Do not catch it inside the unit, suppress real errors or skip the explicit final read checks. This leaves nonce/transition/SQL/event counters unchanged on replay, without dynamic global write flags or nested units. Actual I04 must verify both the ordinary read branch and this concurrent-commit race after fresh-process response loss.

## 7. Constructible imported corpus and digest domains

RA1 initially supports one **new closed authored imported** fixture profile, no historical live outputs. Build a new canonical raw record from exact approved source hashes, fixed run/job/timestamp, explicit six outcome-only observations (including the API outcome that is then withheld before job construction, leaving five job observations) and **empty traceText for every observation**; arbitrary extra fields, nonempty trace/secret/unknown ancestry or unregistered provenance deny the whole reasoning release. The registered schema/field map covers every byte of that frame; this is not a general log sanitizer. Existing `build_job` then emits literal failure reasons `fail`, retaining absent API coverage without copying traces. New private sources `vf1-execution-record` and `vf1-coverage-policy` remain **restricted**, including for Admin and ordinary export.

The trusted catalog separately permits the independently authored outcome fields + approved eight safe source files and closed frame metadata for reasoning. Explicit fixed-field lineage/extraction authorization is private and project/policy/version bound; it does not change classification of the private originals or inherit ordinary report-read permission. Legacy rt_sources.lineage `registered_operator_bytes` alone cannot prove this authority. Do not call frozen RC1.check_scope/Harness to authorize this new raw-record profile: its contextRecord/outcomeRecord predicate is a different offline corpus. Reuse only its envelope/mapper/shape primitives where compatible, with new server lineage/current authority checks and unchanged core.

The **pure feasibility probe** constructs this new raw record/job, authored proposal, `execution_projection.project` expected bundle and `report_lineage` before any future intake. It proves bytes/shape/projection compatibility only. Freeze this corpus target at **projectConfigVersion=2, dataPolicyVersion=2** before registration. In a fresh exclusive namespace, project_create returns1/1 with sourceIds empty: normal intake here denies source scope, and a1/1 bundle cannot run after the required configure increment. The trusted operator first registers the exact2/2 bundle and all pinned sources while project is1/1 (register_snapshot does not require current target-version equality), then Owner/Admin project_configure with expected_config1 enables exactly the eight report-source IDs from the registered catalog and asserts returned versions2/2.
