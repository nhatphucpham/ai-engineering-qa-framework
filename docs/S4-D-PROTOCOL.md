# S4-D v1 — active lifecycle, trusted local synthetic slice

Written 12/11/2026 before source and execution. Baseline S4-C remains unchanged. Compose its authenticated assignment and real owned helper with a versioned active lifecycle in the same schema and common identity mutex. IAP-A queued state is a compatibility authority record, not the lifecycle result; a database trigger prevents its queued cancel shortcut once an S4-D lifecycle exists. The harness directly calls trusted in-process Lifecycle methods; there is no client-facing facade, request whitelist, or network endpoint, and no claim about untrusted dispatch. No remote authentication, restart recovery, arbitrary execution, artifact/report or product gate claim.

A consumed live job is enrolled as active before lifecycle operations. A user cancellation uses the same live session, scoped cancel grant and Runner ownership rules as IAP-A, and atomically reserves cancellation, fences the lifecycle and records a durable request bound to job, generation, assignment, attempt and original fence. Trusted worker completion uses current service/delegation/assignment checks under the same mutex and atomically reserves completion with its own cleanup request. Both compete for one active row; only one wins. Neither reservation is terminal. Completion here means the fixed synthetic job has been stopped and observed clean, not a report accepted or published.

Only the trusted local controller can contact its registered helper. Actual S4-C cleanup validates owned helper generation/job and processes, cgroup and container removal. Then a DB transaction validates exact request/job/original fence and observed cleaned state before terminal transition. Client-supplied cleanup booleans are not accepted. Failure leaves request pending and blocks another job. Explicit DB-clock timeout changes lifecycle to failed_cleanup_unconfirmed and records open incident. A later actual cleanup acknowledgement resolves resource blockage and incident as late cleanup, but preserves failed terminal history; no automatic retry. A forged, wrong-request, stale-generation or replayed acknowledgement cannot advance state. Cleanup is allowed after authority revocation. Crash/restart reconciliation is out of scope.

Acceptance, all NOT RUN at initial protocol creation: D01 active cancel with actual live descendants, durable cancelling before cleanup and terminal cancelled only after exact observed cleanup; old queued shortcut denied. D02 cleanup outage/timeout with open incident and blocked new attempt, late real observation closes incident without rewriting failed terminal or dispatch retry. D03 both ordering directions of completion versus cancel on common mutex, one winner and real cleanup before terminal; stale competing operation denied. D04 wrong request/generation and replay denied, original live container/state unchanged until proper cleanup. Run fresh isolated schema and unique evidence file, before/after source hashes and credential scans, actual cleanup/finally. Results remain pending independent review and actual runner checks.
