## Protocol s4-c-1.0.0 / launch ordering

- Exact version/route/field whitelist at local worker facade. `prepare` authenticates worker service against current assignment/project/run/attempt/fence/delegation/user/policy/service epochs using the common held identity mutex. A new durable job binds that exact assignment and trusted helper generation. One outstanding unclean job per project/run, unique assignment forever; no automatic retry. Worker IDs/authorized/cleanup booleans are never accepted as authority.
- `release` is owned controller operation: confirm job registry/generation; authenticate worker + original exact assignment again, then atomically change prepared→consumed under common DB mutex/final DB-clock deadline checkpoint. Consumption commits before external IO; immediately dispatch fixed launch on same owned helper channel, no queue/reusable permit returned to workload. Duplicate consumption cannot dispatch twice. DB/call failure after consumption means **uncertain**, never automatic replay; job remains consumed until observed cleanup.
- Revoke commit before consumption → consume denied, no workload launch. Consumption commit before revoke → launch may have begun or occur in-flight; no promise of undoing that effect. Next explicit controller supervision/check denies further authorized operations and initiates stop/cleanup. This experiment does not implement continuous service polling/delivery/latency guarantee. DB transaction does not remain open across engine IO.
- Cleanup is reducing authority even after revoke/expiry: no fresh worker credential needed by trusted controller for its own registered job. Helper observes exact owned container/PIDs+start-times and cgroup, stops descendants and removes that exact container, verifies no live original processes/cgroup population/container remains. Only owned channel generation/registered job observation can update job to cleaned. No public cleanup-ack route, caller flags, unrelated ID, metadata retirement or process exit alone accepted as proof. Failure/lost helper/generation mismatch leaves consumed/prepared unresolved, blocks new admission; no forged successful terminal.
- `cleaned` means observed resource cleanup for this local job only. It never means app cancelled/completed/report_ready. Existing IAP-A queued cancel is not exposed by this bridge as an active-run cancel protocol. No new app terminal transition, retirement/retry/lease lifecycle, output release/sanitizer/secret broker. Host/Python/DB compromise excluded. No worker-host crash/restart reconciliation or latest-authority restore proof.
