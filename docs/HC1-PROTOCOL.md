# HC1 1.0.0 — bounded host orchestration

18/11/2026. Baseline `bef018e4cbbf1696627ec5c7ca4f455a062b9d0e`, clean master at start. The new-chat delegation authorizes continuing synthetic development after the completed VF1 push. This protocol is written before HC1 code/execution. P4-D/P4-A experiment, not a production platform/SDK/transport decision. Independent reviewer `/root/review_connector`, GPT-6.2 Astra high, assigned at start.

## Goal and boundaries

Reduce session file-port work: one collection command freezes and executes fresh A/B; dispatch returns a versioned offer and caller-held ticket; completion validates the proposal, calls unchanged VF1 bridge/core and generates a fresh narrow dashboard automatically. The agent still echoes runId/jobId/jobDigest from its offer in the native VF1 proposal; the trusted completion entry point wraps that proposal with the separately held dispatch ticket, without rewriting its anchors. No manual report derivation or separate viewer-build command. Existing VF1 code/evidence and MOCK-06 remain unchanged. HC1 scope is the same historical v1 AC01–04; AC05/v2 whitespace stays outside.

There is no selected unattended host adapter. Native host agents are invoked by this authorized session using collaboration tools, receiving only their offered job and response schema. Saving their response and calling completion are still session-mediated. A platform-neutral callable port supports conformance tests; scripted test proposals are explicitly authored transport tests, never live reasoning evidence. Missing connector returns `waiting_connector` and no report. This slice does not implement self-host auth, ordinary export, S4-F recovery, provider adapters, native Windows client, P5/P6 or approval. No real account/project/API/key, packages, publish or commit/push.

## Contract and trust

Trusted caller owns fixed collection policy and all identities; external content is data. Use existing rootless VF1 executor sequentially, fresh run/job/staging namespaces and actual observed cleanup before proceeding. No rerun or collection resume after uncertainty. Preserve staged byte hashes through execution → offered request → dispatch → core → view; never reread mutable source to relabel old execution. A offers all nine observations; B withholds only API page/size before reasoning, retaining full execution privately.

`hc1-dispatch-1.0.0` binds random attemptId, runId/jobId, jobDigest, executionSha256, requirement/candidate versions, absolute UTC deadline, responseContractDigest and caller-supplied transport metadata. The offer embeds the complete native wrapper/nested schema and host instructions; no old proposal is needed. `dispatchDigest` is SHA256 of canonical finite UTF-8 JSON. The caller retains it independently of the response and passes it to completion/cancel. The model returns only the existing `vf1-host-response-1.0.0` proposal inside `hc1-completion-1.0.0 {dispatchDigest,response}`. It cannot choose native model/provenance, outcomes, statuses or approval. Metadata records the session's actual launch configuration, not attestation or measured usage.

Unsupported version, wrong held ticket, sibling/stale response, nonoffered reference, revision/source/execution mismatch, deadline or cancellation reject before report publication. An immutable dispatch is issued once per run; duplicates return the same ticket without invoking again. No automatic retry after dispatch (including transport exception). Missing result stays `waiting_response`; known deadline expiry is `expired`; invalid proposal can be corrected on the same attempt before deadline, with submissions archived. No new checks are requested by proposal contents.

Single-writer mutation uses an exclusive lock directory. Concurrent mutation rejects; an abandoned lock is an explicit unresolved incident, never auto-deleted or replayed. Output generation prevalidates and builds a complete result in a private temporary directory, then renames it to an immutable accepted directory under the lock. Exact repeat completion verifies the complete published byte set and returns the same receipt; different completion rejects. Publication stores proposal, derived internal files, narrow viewer-data, dashboard and hash receipt together. No mutable latest pointer or cross-run batch partial overwrite. Cancellation and completion serialize: cancel-first rejects acceptance; acceptance-first rejects cancel. This is local trusted filesystem coordination, not durable worker/model exactly-once execution or machine-crash recovery. File corruption/partial temp data is an incident; no success from metadata alone.

Final producer is `hc1-orchestrator-1.0.1`: replay recomputes core and projection to validate every output and exact receipt metadata, rather than trusting a self-described receipt hash. Compatibility requires the same producer/contract/template inputs; experimental prior producers stay historical and are not rewritten to pass new replay. Cancelling does not prove termination of an already running native model/callable.
