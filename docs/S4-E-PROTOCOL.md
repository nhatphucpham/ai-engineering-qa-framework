# S4-E 1.0.0 — trusted-local crash reconciliation

Written 13/11/2026 before code/run, baseline `803f5aa`. Selected P3-B/P4-C synthetic experiment; all acceptance initially NOT RUN. Existing S4-C/D source and evidence remain unchanged. No production runtime/stack, remote authentication, TLS, host/engine reboot or general database rollback protection is implemented.

The server commits a unique job/assignment/attempt/fence, original helper generation and deterministic container name before one-use launch. A rootless Linux supervisor owns a private marked engine and fsynced journal; its replaceable helper child may crash without automatically destroying the workload. Intent precedes engine IO. Discovery compares full container ID, deterministic name, exact job/generation/fence labels, boot ID, original process start times and cgroup within the owned delegated subtree. A successful complete engine listing is required; inspect errors are not absence. Unknown or multiple resources, missing journal/authority, changed binding or boot identity leave unresolved incident and block cleanup acknowledgement, launch/retry and terminal success. No wildcard/prune/PID-only cleanup.

Recovery is cleanup-only: never resume or replay execution. Under the existing common identity mutex, server recovery retires the original assignment, advances its head fence and records a monotonically increasing recovery epoch. Linux retains an independent per-job epoch witness outside the replaceable helper; each cleanup command must present the server-held exact binding and latest equal epoch, then observation is committed by a server CAS. Missing/mismatching witness or server generation cannot be repaired by trusting a client flag. This detects selected stale server snapshots against a surviving witness; coordinated rollback/loss of both stores, host/engine restart and production anti-rollback are outside scope. Cleanup reduces authority and may proceed after worker revocation, but requires exact resource ownership. All methods are trusted internal test facilities, with no public endpoint or client cleanup boolean.

Epoch advancement and destructive cleanup are serialized through the complete side effect in the owned supervisor. An old cleanup paused before taking that serialization boundary must recheck its epoch when resumed; a newer epoch winning first denies the old command without resource mutation. E03 includes this ordered real-helper race. E02's injected crash point is after full resource identity has been fsynced, before the controller receives the launch response; a crash earlier than full identity durability is unresolved in this version.

Publication ordering (S4E-RV-01): first persist loss/incident. In a second transaction holding the common identity mutex, reserve the next server epoch and fence assignment, then advance the Linux witness through its serialized request loop, then commit server publication. No newer server epoch is authoritative before the witness rejects old commands. A witness advance followed by failed/uncertain DB commit leaves unresolved mismatch; this version does not guess or lower the witness. The acceptance check holds that transaction in a separate controller process before its witness call; an independent DB connection must still see the old epoch, then the witness advances before commit and a previously paused cleanup is denied. Linux supervisor and pipe relay survive both selected controller and transport-helper crashes; whole supervisor/host/engine loss is outside this experiment.

Exact latest head (S4E-RV-02): the job retains its original assignment/attempt/fence and a separate recovery fence. Each recovery publication compares the exact current head and original assignment state; a newer attempt or unrelated fence denies recovery without changing the new authority. Immediately before destructive cleanup, recheck the same head/epoch and hold the common mutex through engine IO and acknowledgement, preventing scheduler publication in the gap. E06 checks newer-head denial; E07 uses a separate blocked scheduler process and observed PostgreSQL lock wait during actual cleanup. E05 advances the witness then injects loss before server commit and must remain unresolved. E03's transport outage is an actual local controller relay pipe disconnect before Linux command dispatch; it does not prove a remote/network outage. Test-only exact safety teardown for deliberately unresolved E05/E06 does not acknowledge cleanup to the server or clear incidents.

Process loss opens durable unresolved recovery state. Successful fresh reconciliation observes original processes absent/not live (PID plus start identity), cgroup empty/removed and container absent from a successful private engine listing before closing resource incident. Historical crashed execution stays failed; no completed/cancelled/report-ready or automatic retry. Missing latest authority or observation keeps unresolved. Controller loss means an actual Windows controller child is abruptly terminated after a committed launch; helper loss means an actual Linux helper exits abruptly leaving an observed live orphan under the surviving supervisor. Neither is host restart.

Acceptance: E01 actual controller kill/restart, live orphan discovery, durable incident/fence and fresh exact cleanup; E02 actual helper crash/replacement with durable launch intent, orphan recovered even when controller missed launch result; E03 loss/ambiguous/stale authority or mismatched job/generation/container/process binding and helper channel outage cannot mutate target or acknowledge cleanup; E04 stale epoch/replayed observation denied, missing cleanup proof blocks retry/terminal, late exact cleanup resolves resource incident while execution remains failed. Tests use fresh schemas and evidence filenames, raw input hashes before/after/current, canary scans, actual unit/cgroup/container/process cleanup and marker-bound DB stopped at handoff. Root serializes shared DB/WSL execution; independent high-model reviewer keeps stable S4E-RV IDs until CLEAN. DONE applies only to evidenced selected scope.
