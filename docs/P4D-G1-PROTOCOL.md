## Official semantics checked 24/11/2026

- [Webhook headers](https://docs.github.com/en/webhooks/webhook-events-and-payloads): delivery GUID identifies a webhook event. [Redelivery guidance](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header) retains that delivery header on redelivery. Neither documentation establishes equality with a timeline event ID.
- [Ready event properties](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types#ready_for_review): event ID identifies the timeline event; documented commit_id refers to a commit referencing the issue. It is not documented as the historical PR head for this transition.
- [Timeline endpoint](https://docs.github.com/en/rest/issues/timeline#list-timeline-events-for-an-issue) is paginated, with page/per_page (maximum 100). [Pagination guidance](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api) follows response links. Page numbers and timestamps do not establish complete immutable history.
- [Signature validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) must precede processing actual webhook deliveries. G1 has no public receiver or signature verifier and cannot claim authenticated GitHub integration.

Design inference: these reviewed fields do not establish a common occurrence plus exact event revision. Provider-shaped observations stay unresolved even when their payload contains head SHA, commit_id, timestamps or purported proof fields. No current-HEAD/nearest-time/SDK fallback. This is a documented gap, not a claim that no possible GitHub correlation method exists.

## Versioned trusted offline contract

`p4d-g1-1.0.0`, exact fields, finite canonical UTF-8 JSON, max page 64 observations / 64 KiB. A page has `version,project,stream,expected,next,observations`. Cursor values are nonnegative strict integers; next=expected+1. Stream is project/repository/PR scoped by trusted registration, not caller-chosen repo access. The namespace has no public HTTP route and rejects other versions/unknown fields. This trusted local port calls the unchanged candidate Application.dispatch operations; it grants no HTTP caller the operator registration capability.

Observation exact fields: `kind,body`. Kind is `webhook`, `timeline` or `snapshot`; callers cannot choose a separate receipt ID. Synthetic webhook body has repository.id, number, pull_request.number/head.sha, action=ready_for_review and delivery (trusted fixture header projection). Timeline body has repository.id, number, event.id/event=ready_for_review and historyComplete (strict boolean). Snapshot body has repository.id, number, head.sha, draft and historyComplete (strict booleans). Positive integer subjects are independently validated (no bool/float). Webhook receipt ID is webhook:<delivery>, timeline is timeline:<event.id>, snapshot is snapshot:<canonical-body-sha256>. Delivery tokens are bounded ASCII; this mapping belongs to the trusted fixture transport and does not authenticate real headers. There is no caller alias that can bypass delivery dedup. Extra opaque body fields are data and participate in the digest. Body is bounded opaque provider-shaped data and cannot choose commands, paths, policy, proof or run identity. Trusted setup registers each stream's project/repoId/PR and its integration actor (a dummy user exercising existing start authority, NOT an enrolled production integration service). Webhook body subject/action/head, timeline subject/event/id and snapshot subject/head/historyComplete are validated independently. All unpaired observations persist `unresolved` with an explicit reason; incomplete history stays a gap.

An operator-only fixture proof registration, absent from observation/page fields, binds exact canonical observation digest, stream, project/repo/PR/action, canonical occurrence token, exact 40-lowercase-hex synthetic revision and registered snapshot+run identity. Its mode is always `trusted_synthetic_pairing`, never provider_verified. A trusted registry may bind webhook and timeline observations to the same occurrence; each must independently match its full observation digest. Snapshot/current-state observations and history-gap observations cannot be resolved by this seam. Proofs are immutable and owned by setup, not imported from S5 assertions or observation claims. Webhook head must equal proof revision; timeline proof occurrence must equal timeline:<event.id>. Snapshot candidate revision, run ID, config and source digests must match the registered application snapshot. Distinct occurrences require distinct snapshot/run identities even at the same SHA.

Durable unique keys: receipt `(project,stream,observationId)` pins complete observation digest; binding `(project,repoId,PR,pr_ready,occurrence)` pins revision AND snapshot/run. Cross-ingress dedup uses that binding, not SHA or transport ID. Contradiction quarantines the binding permanently, preserving the original binding/run and both observations; never creates a second run or cancels/relabels prior evidence. Same receipt ID with different bytes is a conflict and rejects the page. Unknown/missing/malformed proof cannot create intake/run. Replaying an exact committed page is idempotent only under current authority, same page digest and cursor predecessor; stale/different/ahead pages reject. New observations cannot sneak into an old page.

## Transactions, authority and recovery

Use a new per-campaign schema extension with `g1_` tables/version marker under the existing identity mutex. No old schema migration. Two phases deliberately separate durable intake scheduling from application admission:

1. Receive validates the entire page before mutation, then atomically stores receipts, immutable occurrence binding, quarantine changes, pending plans and local cursor using one Store.unit write / one external authority witness. No application dispatch occurs in this transaction. An accepted cursor means every observation has a durable unresolved/quarantined/pending record, not that a run exists.
2. Explicit drain uses immutable plans and unchanged Application.dispatch intake_snapshot then run_start in separate transactions. Each command uses the same actor, deterministic project/occurrence-scoped idempotency keys, setup-owned run/snapshot and frozen exact config/grant. Before each command, a read-only Store.unit checks binding not quarantined, current grant/session/role/config/source scope and identity; the surrounding identity mutex remains held through that ONE dispatch transaction. No outer Store.unit write wraps another write unit. Each committed dispatch has its own final witness/SQL transaction. A final separate ledger write may store the resulting run receipt only after run_start success; response loss before that write is handled by exact API replay. Incomplete intake with no run remains pending, never execution evidence. A conflict that arrives between phases blocks the next command, preserving any prior intake without creating a run.

Before receive/replay/drain, recheck current session/project start role, enabled config, integration grant, project/stream registration and exact config version. Before any application intake, recheck source scope, registered candidate/run/snapshot/digests, existing receipt/run collisions and queue budget under that same mutex. Exact owned committed intake/start receipts bypass NEW queue-capacity/run-existence checks on replay after their exact original request digest is verified; current authorization/source/config checks still apply. Different-body/snapshot/owner collisions fail. A run occupying its own sole queue slot must replay successfully after run_start response loss. Expected capacity/input/policy failure before intake has zero new application effects; malformed or same-ID/different-byte pages reject before receive writes. Capacity can change between intake and start; start then denies safely with a retained intake/pending plan, with no automatic retry or relabelled success. Revoke committed before admission denies the next phase; previously committed ledger/intake remains historical. Credentials never persist in plans. Revoke cannot commit while an admitted command holds its mutex. No secret/raw provider content is released through ordinary APIs.

A lost response after DB commit permits explicit same-page/drain replay after reopen: unchanged API idempotency and ledger keys prevent extra intake/run/initial events. Replays reauthorize currently and do not invoke QA/reasoning. DATA-CONTRACT section 7 / TARGET-ARCHITECTURE section 4 atomic occurrence-to-initial-run/provider-cursor requirement remains OPEN for full P4-D. The local inbox cursor/pending plan split is a bounded conformance choice to reuse unchanged API admissions without multi-witness transactions. G1 does not claim atomicity across receive/intake/start or automatic reconciliation of unresolved observations. Test loss after receive and after run_start before completion marker, including maxQueued=1 fully occupied by that same run; different-body/snapshot/owner replay must deny.

A true failure after a witness write but before its ONE SQL commit still creates the existing fail-closed authority incident. No success/retry guessed on reopen. Test a precommit rollback/reopen denial, observe rolled-back application rows absent, and retire that disposable campaign schema without repairing it. G1 never presumes exact-XID recovery succeeded. Multi-witness outer transactions are forbidden; extraordinary infrastructure/expiry failures retain incident evidence and need separate operator recovery, not automatic replay.
