## 1. Boundary and version

`p4d-rc1-1.0.0` specifies an internal offline conformance envelope, not an HTTP route or a change to `m50-application-1.1.0`. No implementation, new provider/host invocation, DB/WSL/container campaign, installation, target/SDK/production stack decision or Git mutation is part of this output. Official documentation reads are research, not provider API execution. Three independently implemented future ports are `local_host`, `openai`, `anthropic`; sharing validation primitives is allowed, sharing one fake provider as proof of another is not.

The initial fixture profiles are local completion, OpenAI Responses-shaped non-streaming output, and Anthropic Messages-shaped non-streaming output. These are test dialects, not a production API/model choice or universal API compatibility. Fixtures must carry profile version, authored origin and reviewed source URL/date. New endpoints, streaming, tools, background jobs, conversation continuation, caches/files/attachments and SDKs require another reviewed profile. Unknown versions/fields in RC1 envelopes reject. Unknown provider output block/stop kinds are unsupported, never silently ignored to extract a convenient answer. Documented ancillary metadata may be retained privately by a profile parser but cannot grant authority.

## 2. Exact context and authority separation

Use existing `runtime_candidate.common.strict_json/canonical/digest`: UTF-8 finite JSON, duplicate keys rejected, sorted keys, compact separators, no Unicode normalization. RC1 attempt/artifact/project/run IDs use existing identifier syntax. Preserve producer-specific identity grammars: application assignment/effectNonce are exactly 32 lowercase hex UUID strings (including digit-leading values), fence is a positive strict integer; VF1 jobId and target revision/task/handoff strings follow their existing contracts rather than being rewritten as identifiers. Digests are exactly 64 lowercase hex; strict integers exclude bool. Whole offer and raw response each at most 64KiB; at most 64 source entries, no duplicate artifact IDs; no dynamic path/URL reads. These are offline workload caps, not product SLOs or provider context limits.

Trusted issuer builds an offer with exact fields:

`version, attemptId, port, profile, target, assignment, fence, effectNonce, job, jobDigest, executionDigest, sourceManifest, responseContract, responseContractDigest, policyPin, budget, deadlineUtc`.

- `version` equals RC1; `profile` is `local-completion-1`, `openai-responses-1` or `anthropic-messages-1`, matched to `port`.
- `target` has exact `projectId,runId,handoffId,taskRef,candidateRevision,requirementVersion,projectConfigVersion,dataPolicyVersion` from the existing issuer-held core target; version integers positive. assignment/fence/effectNonce and executionDigest are held application values, never generated by a response.
- `job` is the frozen VF1-compatible reasoning request already used by `execution_projection.project`; `jobDigest` hashes its entire canonical bytes. `sourceManifest` entries have exact `artifactId,revision,sha256,bytes,lineageIds,classification`; length is nonnegative, lineageIds sorted unique IDs, classification is issuer-owned `safe`, `restricted` or `secret_tainted`. Every job byte/observation must resolve to the manifest's exact immutable sources and accepted execution; composite summaries preserve the union of influencing source IDs. Denied sources or unknown lineage block the entire offered job, not an undocumented truncation or summary rewrite. RC1 does not add fields to or rewrite an existing job. A reduced test job must already be constructible using the existing VF1 coverage-policy mechanism, have its own jobDigest, and preserve omitted-observation details in that mechanism plus the trusted fixture registry; otherwise unsupported. It cannot be called the full job.
- `responseContract` has exact `version,schema,instructions`, frozen from the existing HC1/M50 VF1 wrapper with the bound-evidence review relation. It is not just the nested assessment schema. Its digest includes instructions and schema. `policyPin` has exact `configVersion,policyVersion,scopeDigest,capabilityDigest`; it binds an issuer-owned registry record, never a client boolean permitting outbound. Scope digest includes project/port/source lineage; capability digest binds enrollment and context/tool/outbound limits.
- `budget` has exact `maxInvocations,maxSubmissions,inputTokenBound,maxOutputTokens,maxResponseBytes,usageMode`. Initial values: 1 invocation, 1 submission, 64KiB response cap; positive strict integer token bounds supplied by trusted fixture configuration; usageMode is `authored_fixture`. The registry bound by policyPin.scopeDigest independently owns a budget account `(projectId,runId,policyVersion)` with fixed input/output token capacities, no time-window reset in RC1. Attempts cannot create a new account or set remaining balances. Immutable unique `(account,attemptId)` binds exactly one offerDigest; same ID/different digest conflicts before any reservation, receive-handle allocation, send or replay, even when enough budget exists for both. Reserve the vector `(inputTokenBound,maxOutputTokens)` atomically against that shared account; exact replay does not reserve again, different attempts competing for one remaining allocation cannot both send. No actual token or cost measurement is implied. An absent reliable input/output bound in a future live profile blocks automatic invocation until a separately reviewed conservative policy exists.
- deadlineUtc is an issuer-set UTC RFC3339 whole-second timestamp ending `Z`, strictly after admission time. Future integrated effective deadline is the minimum of this value, current lease/run/grant/service limits; a cached client timestamp cannot revive any expired authority.

Caller retains `offerDigest = digest(offer)` and authority separately. A response cannot supply a replacement offer, policy, source manifest or budget. Provider request IDs and model strings are provenance, not this binding or authentication. No bearer, lease token, key, secret reference or host absolute filesystem path goes into the model job. Existing approved inert relativePath/source locators are allowed as source data, never instructions to read files. Internal effect/assignment references may be kept in the envelope; profile encoder sends only the allowed job and response contract, not the internal authority fields. Encoder must not add hidden workspace history, prior responses, expected conclusions, tool definitions or extra artifacts.

The existing VF1 wrapper echoes jobId/runId/jobDigest, not an attempt nonce. Therefore the issuer must also own a private one-shot receive handle bound to `(attemptId,offerDigest,port,profile,sendIntent)` and the exact trusted invocation. The handle is neither in model output nor selectable by a file/response sender. Offline fixture ingress uses that held handle and an operator-registered delivery-to-handle mapping; foreign/missing/duplicate/conflicting delivery channels reject or remain unresolved. Never attach an arbitrary response file to an attempt by computing matching metadata. Future live connectors need authenticated receive-channel correlation before acceptance. Identical bytes legitimately delivered on the correctly enrolled channel prove only transport correlation, not fresh/native/model identity; identical bytes copied from a sibling with the same job but different attempt/policy/port on the wrong handle must reject. If the transport cannot distinguish that misdelivery, capability remains blocked/unresolved rather than claiming correlation from the wrapper alone.

The issuer-owned capability record hashed by policyPin.capabilityDigest also has a fixed `routeSelector,modelSelector,enrollmentSelector,responseModelMap,requireModelEcho`. These are arbitrary authored fixture tokens (for example routeA/modelA), not a chosen real endpoint/model/platform. Request routing and model configuration are separate from model-visible job content. Before releasing any bytes, compare encoder's actual selected route/model/local enrollment to the pinned selectors; missing/different selections block capability, including substitution on the first and only invocation. No environment/default override or same-provider model fallback. For API profile fixtures requireModelEcho is true; responseModelMap is a configured set of permitted documented model echoes for the pinned selector, never learned from that response. Apply this echo check only to an otherwise candidate-eligible parsed success on the trusted receive channel, immediately before candidate_received: missing/unmapped/contradictory echo yields unsupported/output_kind and no validated candidate. Earlier error/refusal/incomplete/timeout/transport-loss dispositions in §4 take precedence and remain unchanged even without a model echo; a 429 without model is provider_error/rate_limit, a timeout without model is unresolved_send/timeout. For the local profile model echo may be unavailable (requireModelEcho=false), but enrolled routing must still match the bound handle; this proves routing only, not the native model. Model strings remain provenance and cannot by themselves authenticate the route. Any future profile unable to enforce its declared selector/mapping remains blocked/unresolved rather than inventing attestation.

No existing project config enables actual outbound: API1.1 enforces `outboundProviders == []`. RC1 fixture policy registry simulates decisions only; it cannot authorize a model call or bypass that check. Likewise a local fixture's declared capability is not proof a broad-workspace native host has isolation. Missing enrollment or enforceable context/tools/outbound control returns `blocked_capability` with zero release/invocation. Research documentation and historical session reasoning do not enroll a new connector.

Manifest classification names are RC1 policy categories: `safe` maps only from independently registered `safe_source` with allowed lineage/current policy, or a separately enrolled permitted derivative with complete extraction/lineage. Existing registry `restricted` remains restricted; secret-tainted inputs stay denied regardless of spelling. No caller/provider manifest may reclassify those bytes. Even safe_source does not bypass project/port/data scope.

## 3. Attempt, cancellation and replay

Proposed offline attempt states are local ledger states, **not** application run states: `offered → send_intent → candidate_received → candidate_validated`; alternatives `blocked_policy`, `blocked_capability`, `blocked_budget`, `refused`, `incomplete`, `malformed`, `unsupported`, `provider_error`, `cancelled_fenced`, `expired_fenced`, `unresolved_send`, `accounting_unresolved`. Candidate validation is not assessment acceptance/report completion. Record immutable attempt/offer/response digests and separate status transitions, never edit the original result into a success. Accounting reconciliation may move accounting_unresolved to candidate_validated only for the same private candidate, before expiry/cancel/current-authority loss and after all validation; it cannot change a failure/refusal/cancel/expiry into success.

Before send_intent: verify all context pins, current policy/capability, effective deadline and whole-attempt reservation; commit a one-use send intent and reservation before handing bytes to a port. Commit failure or unknown authority blocks send. No lock is held across a remote call. Actual bounded context release must reauthorize and serialize each release with revoke; current API ordinary read hooks are not a reasoning gateway. An integrated gateway needs its own reviewed release/fence implementation before this step can run against any external/host port.

The offline runner models these boundaries with controlled clock, explicit fault checkpoints and invocation/release counters; it proves local decision logic only. Future integration requires actual DB/CAS/current authority and process reopen, not a clock stub labeled production recovery. Two admissions for the same attempt/offer must consume at most one intent/reservation. If crash/response loss leaves uncertainty after intent, reopen keeps `unresolved_send` and the reservation; no repeat send or new attempt, even if no request ID was recorded. Explicit replay may read/validate the exact stored receipt under current authority, never invoke again. Missing/damaged/conflicting receipt is unresolved, never inferred success. This does not promise exactly-once remote execution.

Cancel and candidate acceptance serialize on the same future server attempt fence: cancel-first blocks acceptance/publication even if bytes arrive later; acceptance-first records the accepted candidate and rejects changing it, while ordinary run_cancel still uses the existing application lifecycle before publication. Revoke/lease expiry/config changes before acceptance or worker_submit deny new effects. Deadline equality is expired. Cancellation/deadline fences local acceptance; transport close/cancel request is best effort, **not** proof remote computation or billing stopped. Keep remote termination `unknown` absent an authoritative observation; do not mark the app run cancelled or QA cleanup from an RC1 status. Late data may be archived privately for accounting, never accepted.

No automatic retries, continuation, corrective model calls, SDK retries, fallback port/model, hidden truncation or budget expansion. RC1 has one submitted candidate; malformed output ends that attempt. Historical HC1/M50 explicit corrections remain unchanged, not reinterpreted as RC1 evidence. A future explicitly requested retry needs a new versioned policy/attempt with reconciled ambiguity and remaining budget, outside RC1.

## 4. Separate result profiles and accounting

Each trusted port mapper returns an RC1 result with exact fields `version,attemptId,offerDigest,port,profile,outcome,diagnostic,responseSha256,proposal,usage,provenance`. Version equals RC1. Closed mapper outcome/diagnostic pairs are `candidate_received/none`, `refused/refusal`, `incomplete/output_limit`, `incomplete/context_limit`, `incomplete/terminal_incomplete`, `malformed/parse`, `malformed/shape`, `unsupported/output_kind`, `unsupported/stop_reason`, `provider_error/auth`, `provider_error/permission`, `provider_error/rate_limit`, `provider_error/overload`, `provider_error/service`, `provider_error/unavailable`, `unresolved_send/timeout`, `unresolved_send/transport_loss`. Local pre-send failure uses attempt blocked_capability or blocked_policy, not a fabricated mapper result. Expiry/cancel and usage incidents are ledger dispositions after mapping, not mapper assertions. Use terminal_incomplete when an explicit incomplete terminal marker has no documented output/context-limit reason; do not invent a limit cause. Queued/in-progress/unknown terminal states in this non-streaming profile are unsupported/stop_reason, never candidate.

`proposal` is null unless mapper outcome is `candidate_received`; it then holds the unchanged `vf1-host-response-1.0.0` wrapper. `responseSha256` hashes exact received body bytes (null only if no body); strict parsing and schema/core validation follow. `usage` has exact `mode,inputTokens,outputTokens`; mode is `authored_fixture`, nullable strict nonnegative integer counts. Unknown usage is null, never zero. The trusted ledger alone records reconciliation and balances, never a mapper-supplied `reconciled` flag. `provenance` has exact nullable `requestId,model` strings bounded to 256 characters, plus `origin=authored_fixture`; no raw diagnostic text. Bound total receipt size to 64KiB. Caller verifies receive handle first, then compares all result anchors with the held offer/registry; copied mapper anchors do not establish a receive binding.

Offline local ingress is a trusted fixture transport event with exact `kind,body,usageCounts` fields, selected by fixture setup rather than the model. kind is `completion`, `refusal`, `output_limit`, `unavailable`, `auth_error`, `permission_error`, `rate_limit`, `service_error`, `timeout` or `transport_loss`. body is raw bytes for completion/refusal, nullable for output_limit and null for transport errors; usageCounts is null or an independent authored pair with exact `inputTokens,outputTokens` fields. Only completion body is a VF1 wrapper; refusal/limit/error events cannot masquerade as wrappers. Thus local error cases do not require invented HTTP fields in the VF1 response. Provider fixtures independently have trusted HTTP status/header/body or transport-loss observations. HTTP 401 maps auth, 403 permission, 429 rate_limit, Anthropic 529 overload; remaining non-2xx map provider_error/service, preserving status only in private fixture evidence. HTTP error status takes precedence over body text; for successful responses refusal dominates incomplete, then unsupported block/stop, then parse/shape checks, then candidate. Missing or ambiguous terminal markers reject shape; never derive refusal solely by guessing natural-language intent.

| Port profile | Distinct input/output mapping required | Noncandidate outcomes |
|---|---|---|
| local-completion-1 | Encodes only offered job+contract; trusted local event kind completion carries a strict VF1 wrapper. No workspace/tool access. Missing connector is zero calls; issuer task metadata is not model authentication | Trusted local fixture event kind maps refusal→refused/refusal, output_limit→incomplete/output_limit, unavailable→provider_error/unavailable, auth_error/permission_error/rate_limit/service_error to corresponding safe provider_error diagnostics, timeout/loss→unresolved_send. A task-ID string cannot upgrade it to unattended/native reasoning |
| openai-responses-1 | Authored object must have object=response, top status=completed and exactly one output item type=message, role=assistant, **message.status=completed**, with one output_text containing one JSON wrapper; no error/incomplete/refusal/tool content. Wrong object/message kind or role is malformed/shape; inner incomplete without a documented reason is incomplete/terminal_incomplete. Never use convenience output_text alone. Known ancillary reasoning items cannot be assessment content; unknown types fail unsupported | Refusal dominates any parseable text; incomplete/max_output_tokens remains incomplete; failed/error/auth/429/5xx are provider_error; timeout or uncertain response loss after intent is unresolved_send. No follow-up/cancel endpoint or polling behavior is assumed |
| anthropic-messages-1 | Authored object must have type=message, role=assistant, stop_reason=end_turn and exactly one text block containing one JSON wrapper; wrong type/role is malformed/shape. No tool/thinking/continuation content in this bounded profile. Empty end_turn is malformed, not success. Usage fields interpreted by this mapper alone | refusal remains refused; max_tokens/context-window stop is incomplete; tool_use/pause_turn/stop_sequence/other stop kinds unsupported; auth/429/529/other errors provider_error; uncertain timeout/loss unresolved_send. No continuation or fallback |

Project policy denial precedes any provider parsing/call and yields blocked_policy. Strict malformed/duplicate-key/oversized/invalid UTF-8/schema-invalid responses never produce accepted assessment or run/report mutations. A completed natural-language refusal lacking a documented machine refusal marker is not inferred to be successful JSON: parsing/shape failure stays malformed. Refusal text itself is not an AC failure. Preserve check assertion failures separately from provider faults, missing reasoning, and human decision pending.

Reservation is held after send intent for every result until usage is reconciled; missing/malformed usage or an uncertain call cannot refund it as zero. Candidate_received with unknown/invalid usage remains private `accounting_unresolved` and cannot become candidate_validated/assessment accepted. Other failure outcomes remain unchanged with unresolved accounting. Complete trustworthy fixture counts release unused reservation only once after validating counts against bounds; over-bound usage yields `blocked_budget` plus an accounting incident and blocks acceptance, never negative budget or a new call. Reconciliation converts reserved amounts into consumed counts plus remaining capacity under the same account lock; duplicate records with same counts are no-ops, changed counts conflict and hold an incident. Accounting is independent of refusal/cancel/late response and cannot revive them.

Per-profile token normalization is explicit: OpenAI inputTokens is the top-level input_tokens, outputTokens is output_tokens (cached/reasoning detail fields are already included and not added); Anthropic inputTokens is base input_tokens + cache_creation_input_tokens + cache_read_input_tokens, outputTokens is output_tokens; the profile treats omitted cache categories as zero only for a complete documented no-cache usage shape, not missing usage. Cache breakdown subfields are not added again. Local counts come from independent authored fixture event usageCounts, never a proposal claim. Invalid/negative/bool or contradictory category breakdowns give unknown counts/accounting_unresolved, not a partial refund. Future live usage must come from the enrolled adapter response. Price/model version and hard monetary-cap enforcement are unknown/outside this design.

## 5. Reuse the application; explicit integration prerequisite

Only validated candidates pass to existing `runtime_candidate.execution_projection.project` → existing core/prepare checks → `Application.dispatch('assessment_accept', assessor, ...)`; independent `worker_submit` remains the sole report publication path. Expected executionDigest comes from accepted collector state; issuer-held job/source/target pins cannot be reconstructed solely from provider echoes. Worker/collector credentials cannot act as assessor. Provider responses never carry credentials, accepted/status/cleanup/approval fields or public operation names. Any extra authority claim rejects rather than granting access.

This chain is a **target for integration acceptance**, not implemented here. API1.1 has neither a reasoning admission route nor server binding to RC1 attempt/offer/cancel/reservation. A client-side precheck followed by unmodified assessment_accept would have a cancel/revoke race; it must not be called integrated conformance. Before integration code, version a narrow internal/server extension that rechecks attempt fence/offer/reservation with current authority in the same acceptance and publication transactions, using the existing single-witness Store.unit discipline. Do not nest witness writes or move credentials to the port. Old API1.1 evidence stays historical; no silently extended allowlist/config schema.

Until that extension is reviewed/implemented, offline mappers emit candidate records only and record dispatch/accepted-assessment/report/event counters as zero. They may exercise pure projection/core with imported fixture proposals, labeled validation only. No fake dispatch log counts as actual API behavior. Required integrated cases use separately registered **imported** synthetic execution with its own new DB namespace, or new authorized executed evidence, never relabel historical execution. No new QA/native rerun is needed to prove an imported transport integration boundary.

Positive corpus prerequisite: author a new clean synthetic VF1-compatible job/response with independent permitted safe sources and outcome-only observations; include explicit extraction/lineage records for every offered byte and preserve failed+gap. Precompute the exact projected bundle using execution_projection.project, register that exact bundle and expected source/target digests before intake, then label collection imported. Imported assessment acceptance requires that exact registered bundle digest, not a newly projected arbitrary bundle. Do not reuse fixture_import's existing restricted host-request.json/execution.json as a positive: their raw trace/reason lineage is not allowed reasoning context, and readside outcome projection is not reasoning-release authority. O05/I02 must deny that unmodified restricted importer without reclassifying it safe because it is synthetic. If a clean constructible corpus cannot meet existing projection/registry rules, mark I01 NOT RUN/blocked rather than weaken policy or acceptance.

## 6. Official semantics consulted on 24/11/2026

These facts inform authored fixture profiles; local state names, strict profile restrictions and fail-closed choices above are project design inferences, not provider guarantees. Refresh and pin the selected endpoint/schema/SDK before implementation that relies on changing provider details.

- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs.md): handle refusals/incomplete/API errors separately; schema constraints do not validate domain/reference rules.
- [Responses reference](https://developers.openai.com/api/reference/resources/responses/methods/create): response status/incomplete/error/content must be inspected; max_output_tokens includes visible and reasoning output; disabling truncation avoids automatic context removal. RC1 does not select a model or assert a monetary cap.
- [OpenAI Python library retries](https://github.com/openai/openai-python#retries): the documented SDK defaults include automatic retries. A future chosen SDK must explicitly disable retries and prove attempt counters at the transport boundary. The repo does not install/select it here.
- [Claude stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons): end_turn may be empty, max_tokens means truncation, refusal is distinct, tool/paused turns are not a completed QA proposal. Documentation continuation/fallback advice is not permission under RC1.
- [Claude errors](https://platform.claude.com/docs/en/api/errors): distinguish auth/permission/rate/overload failures; request-id is a diagnostic, not an application attempt identity.
- [Claude Python SDK retries](https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/python#retries): documented retries also require explicit disabling in any later SDK integration; timeout configuration alone cannot prove one invocation.
- [Claude usage categories](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#tracking-cache-performance): total input adds base, cache-read and cache-creation tokens; nested cache-creation details break down that category rather than add another total. Accounting tests do not enable caching or select a caching strategy.

## 7. Completion boundary

Design DONE requires latest exact audit/protocol/acceptance/handoff plus check tooling/evidence independently CLEAN; static structure/link/preservation checks PASS. All future runtime cases remain NOT RUN. Offline implementation DONE later needs each port's own required cases PASS and independent latest-source review. Integrated DONE later additionally requires all integration cases on the real application boundary. Neither closes full P4-D or grants Git/API/install/pilot/publish rights.
