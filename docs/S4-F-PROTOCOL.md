# S4-F 1.0.0 — whole-supervisor and uncertain-launch reconciliation

22/11/2026. Written before new S4-F source or shared effects. This is a prerequisite of the requested M50 P4-C milestone, not a replacement for its whole authenticated worker/acceptance gate. Baseline `bef018e` plus existing reviewed HC1 and in-progress M50 candidate; all earlier source/fixtures/raw evidence remain unchanged. Root alone serializes owned WSL/PostgreSQL effects. No host/engine reboot, production remote deployment or antirollback claim beyond the actual observations below. No global packages/services, real project/account/credential, Git action, pilot or publish.

## Scope and trusted anchors

Use the retained rootless OCI engine, fixed synthetic workload/check registry and delegated transient systemd units. Pinned project/run/assignment/attempt/fence and one-use server effect nonce precede external launch. A durable engine-context receipt fixes the marker-bound private engine storage, owner/boot/filesystem identity, pinned image/command/mounts and deterministic per-effect container name. A fsynced journal records consumed launch intent before engine IO and full container/process/cgroup identity when observed. The journal is outside the process/unit being deliberately killed. No workspace host command is ever chosen from artifact/model text.

The *whole Linux supervisor* (including its request loop, transient helper children and engine command context) is killed, rather than only the transport child tested in S4-E. The actual original PID/start identity, unit/cgroup and absence/replacement are recorded. Systemd may itself terminate workload descendants when the unit dies; report that fact, never call those descendants live orphans if not observed alive. A fresh supervisor process opens the prior exact private engine/journal with the same boot and separately held server/context anchors. It must not instantiate a fresh empty engine and interpret its absence as cleanup of the original.

Latest server head and an independent durable per-effect witness fence destructive reconciliation. Recovery reduces authority only: never resume a check or replay consumed launch. Before discovery/cleanup take the owned engine/journal serialization lock, establish that the old unit/process group can no longer issue engine IO, verify full server binding/current recovery fence and successful complete engine listing. A listing error, unknown extra container, mismatching generation/job/nonce/image/process/cgroup, missing witness or newer assignment is unresolved; no acknowledgement, new admission, terminal success or automatic retry. No name-prefix/PID-only/wildcard/prune cleanup.

## Required failure windows

F01 — after durable full identity: observe actual workload/container, kill whole supervisor/unit, create a genuinely new supervisor, reconstruct the original context/journal, independently re-observe original processes/cgroup/container, then exact cleanup-only. If systemd terminated descendants, preserve the pre-kill identities and prove they are no longer live; do not claim a live orphan. Execution history remains failed; resource incident closes only after observed cleanup and server CAS.

F02 — after consumed launch intent, before external create: kill at a controlled barrier with no full identity record. Acquire original context/lock and prove old writers quiesced. A successful empty complete listing plus the authenticated original intent and actual old-unit absence may prove no resource remains; retain failed/no-replay execution. Missing listing/quiescence/intent proof stays unresolved. A consumed intent is never reset merely because an acknowledgement was lost.

F03a — after external create/start, before full identity durability: at a real running barrier a separate test observer confirms the container/processes existed, but its test-only PID/CID is not offered to recovery as authority. Kill whole supervisor at that barrier. Fresh reconciliation may derive a full immutable CID only from the successful original private engine enumeration plus exact deterministic intent name, all labels (project/run/job/nonce/attempt/fence), image, configured command/mounts, same boot and owned cgroup/process observations. It must confirm exactly one match and no unknown resources before recording that identity. A name alone is insufficient. Compare the resulting recovered identity with the separately retained test observer only for acceptance evidence. No new launch.

F03b — created-but-not-started, or stopped by actual supervisor/unit loss: a missing live PID/cgroup is not an invalid condition to gloss over. Positive cleanup-only is possible only when independent immutable ownership/intent bindings match the full inspected CID, complete engine inspection says not running with no init PID, original supervisor/unit writers are quiesced and the original owned cgroup has no live descendants (or is absent). Existing captured original start identities must be checked where available. If any of that proof is unavailable, leave unresolved without automatic delete/ack. Test a real created/not-started case separately from F03a and record whether the unit killed a previously running workload. An empty successful listing proves only current absence after quiescence, not that no execution ever happened.

F04 — uncertainty/authority negatives: wrong context marker/inode/boot; absent/corrupt/older journal; incomplete engine listing; wrong job/nonce/fence; changed full process start identity; newer server head; concurrent reassignment; lost channel/DB acknowledgement. Each denies destructive or publication effect as appropriate and preserves incident. Test both lock orderings around latest-fence publication and cleanup; never retire newer authority to make an old cleanup pass. A deliberate exact safety teardown of test resources is separate from a rejected application cleanup acknowledgement.

F05 — supervisor replacement continuity: continuously monitored local executor service detects missing original process, persists failure/incident and uses a fresh process plus durable bindings. A UI/HTTP client closing does not own or cancel it. Lease/credential/config loss stops new effects and triggers cleanup-only; a worker cannot forge collector resource identity or cleanup booleans. The candidate application accepts only the independent actual raw record/held byte pins and resource witness, then any assessment/report must pass its current audience/lease/fence/source/core checks. Bounded fault tests are not a production service install or unattended model connector.

## 1.1 bounded dead-pause anchor repair, before new effects

23/11/2026. Actual r1 exposed that killing the entire original unit also kills Podman4.9.3's namespace pause process. A fresh replacement cannot even list that private store. No r1 cleanup was acknowledged. Diagnostic p1/p2 use fresh engines with no container/check launch; they confirm the pause process belongs to the old supervisor cgroup and that the original context can be observed independently before/after loss. These diagnostics do not repair the old incident.

For new contexts, pin the original pause PID/start identity, exact regular pid-file inode/bytes, UID/GID maps and parent-directory identity while it is live. After original unit/cgroup absence and the current server recovery fence are verified under both existing locks, the replacement may clear **only that exact stale pid file**, after proving the pinned original pause process is no longer live. Persist a bound repair intent before unlinking; no signal is sent to a reused PID. Then allow ordinary Podman information/listing to establish a new namespace helper, check the same private storage/image and identical UID/GID maps, and retain the new helper identity in the repair receipt. This creates no QA container and never resumes checks. A missing/substituted pid file, map mismatch, live old writer or uncertain repair remains unresolved. No `system migrate`, reset, prune or wildcard operation is permitted by this repair.

Only after successful complete original-store enumeration and full immutable resource validation may ordinary cleanup proceed. An unknown container still blocks resource stop/removal and acknowledgement. Clearing a proven dead helper anchor is distinct from deleting or acknowledging any container. A crash midway through this bounded repair is not permission to guess completion or use a fresh engine; retain the incident for explicit operator investigation. Existing r1 contexts lacking these additional pins are not silently upgraded. The approach follows the documented rootless pause dependency, narrowed to an independently proven stale anchor in the one private engine. [Podman4.9.3](https://docs.podman.io/en/v4.9.3/markdown/podman-system-migrate.1.html).

### 1.2 exact runtime-refresh sentinel, before next run

Actual r2/r3 showed that deleting only the stale pause PID anchor does not permit access: the original `alive` sentinel still requests rejoining the dead namespace. Podman's maintainer describes this runtime-refresh boundary for whole-process loss in [issue20697](https://github.com/podman-container-tools/podman/issues/20697). The narrowed next experiment additionally pins the original exact regular `alive` file and `alive.lck` identity, takes the same lock nonblocking, and clears only the two independently pinned obsolete runtime files after proving old process/unit quiescence. No runtime directory, storage database, container, image, unknown filename or arbitrary path is removed. A durable bound intent precedes these changes. Ordinary engine initialization can then refresh private runtime metadata and create its helper; it still grants no cleanup acknowledgement. Full container enumeration/immutable ownership and original process checks remain mandatory before any container operation. Partial repair or changed pins fail closed. This is a new bounded trusted-local recovery design requiring actual evidence and independent review, not retroactive success for r1–r3 or a production engine-restart claim.

Required extra negatives: an actually live original unit denies replacement; an absent or substituted stale PID file and modified alive sentinel deny before repair intent/external engine IO; malformed truncated output denies as listing failure; a separately injected **inactive** unknown container in the same private store denies original-container cleanup while retaining both objects. The test may remove only its exact independently created inactive fault container after verifying its full ID/name/image/nonrunning state, with no application acknowledgement or change to the original object. Execute these under the latest-head DB mutex and original-engine serialization lock, then re-observe the original exact resource before normal cleanup.
