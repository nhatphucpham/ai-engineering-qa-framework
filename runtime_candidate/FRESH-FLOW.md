# Fresh source → execution → native proposal → report acceptance

This acceptance flow is synthetic and target independent. It registers only the eight approved MOCK-06 requirement/source/test artifacts and the unchanged fixed check registry. `fresh_fixture.source_intake` does not read an old observation, assessment or report. The registered core target fixes project/task/handoff/run/config/policy before start. The service's one-use admission supplies the execution job identity and input hashes. The handoff identity is deliberately independent of that raw job identity.

The operator starts a separate monitored worker process through the existing fixed rootless VF1 executor. A transient delegated Linux unit runs the approved checks with nonroot/read-only/no-network/resource bounds; the original worker emits its raw record and the operator independently observes unit and cgroup teardown. A disconnected ordinary HTTP client is not the worker's owner. No artifact or model text chooses a command, container image, resource path or credential.

The private operator observation port checks actual raw bytes, all input hashes, resource identity, fixed job reconstruction and independent supervisor observations against the server-held admission intent. Only then may the separately enrolled collector accept execution through TLS. Raw record and offered job remain restricted late-bound origins rather than invented input artifacts. A worker claiming cleanup or an assessor inventing an outcome cannot establish those origins.

Only the self-contained offered job and response schema/instructions are supplied to a fresh native reasoning agent. Its proposal is saved with the native task and caller-held job digest. The issuer's context adapter constructs new typed core inputs from that proposal while retaining raw source, job and execution provenance. No previous answer or expected criterion status is supplied. Rejected proposals remain preserved; correction is the same native attempt, without rerunning checks or silently editing the answer.

The enrolled assessor submits the exact bundle/assessment/execution digests through TLS. The currently authorized worker publishes through TLS; unchanged core policy determines evidence coverage and verification. Ordinary report, export, source links and persisted outbox are inspected independently. Processing completion is separate from criterion verification and humanDecision remains pending. A checkpoint with populated raw/job observation refs must restore the same restricted bytes and ordinary report. This fresh success path supplements the process-loss, authority/lease/cancel/revoke tests; it does not replace S4-F whole-supervisor and pre-identity recovery or prove a production unattended reasoning connector.

Actual output belongs in a new exclusive M50 evidence batch. Source pins are retained before/after, private tokens stay in the ignored operator cache, old fixture/evidence bytes remain unchanged, and all owned units/containers/database service must be observed stopped before handing off. Until actual evidence and independent review exist, this is an acceptance contract rather than a completed result.

The current operator entry is `py -3 -B -m runtime_candidate.run_fresh <unused-evidence.json> <issuer-observed-native-task-id>`. Arrange an available fresh native task first, then keep the live process handle while it prints `FRESH_NATIVE_OFFER_READY` with its private offer path. That task receives only the offer, never a historical answer or private raw execution. It writes an immutable numbered `native-response-1.json` in the same private batch. After independently observing that task complete, the issuer writes `native-ready-1.json` atomically with exactly `nativeTask,jobDigest,offerSha256,responseSha256,observedNativeCompletion=true`. All anchors must match `native-dispatch.json`; a candidate cannot supply its own issuer attestation. Ready files must not be precreated before observing the actual native completion.

The worker checks the native proposal and unchanged core before assessor submission. A rejection retains the exact response plus `native-rejection-1.json` and prints a safe rejection code. The issuer may ask the **same** native task for a numbered correction and attest that new response. There are at most3 submissions within the original120second correction window and180second absolute run budget; renewal extends only the lease. Missing connector, unavailable model, invalid/partial ready handoff or expired budget does not generate a report. An atomically delivered ready digest, rather than first existence of a response file, marks a complete proposal.

One trusted operator coordinator currently exercises four separately enrolled API audiences. The check workload is a real distinct rootless Linux process/unit; the native task is separately invoked through session tools. This does not claim four independently operated deployed services, a production unattended worker install or authenticated model provenance. The dispatch records the issuer's session observation, with task/offer/response hashes. Raw worker stdout is retained unchanged; an enriched canonical record adds only explicit ingestion policy and has its own distinct hash. Server-approved full input hashes are compared to staged hashes **and** reread staged bytes before starting any external supervisor. A changed byte or misleading stage hash is denied with zero external launch.
