# Restricted recovery of an aborted authority transition

API1.1 uses a single bounded `authority-transition.json` slot. Every writing application transaction records its previous and next external nonce, the exact top-level PostgreSQL xid8, schema/instance and the original cluster marker/system identifier. The next nonce is the first128 bits of SHA256 over that canonical exact transition payload, including its explicit domain/version and a fresh256-bit salt. Recovery verifies this binding against the independently held external nonce before consulting the transaction status. Substituting another valid aborted XID, previous head or cluster cannot retain that nonce. The journal is written and fsynced before replacing `authority.json`; SQL commits last. Any disagreement blocks ordinary operations. These files are private operator state, never public routes or worker assertions.

An operator may call `store.reconcile_aborted_transition(expected_nonce)` only after inspecting that exact uncertain transition. It holds the existing identity transaction mutex and requires the current database nonce to be the journal's previous nonce, the external nonce to be its next nonce, the same physical cluster and instance, and PostgreSQL to report the recorded transaction **aborted**. Committed, in-progress, unknown/too-old, malformed, missing and retired heads remain blocked. A committed transaction whose SQL head appears older is never repaired by trusting the apparent rollback. PostgreSQL describes retained xid8 statuses in its [transaction information functions](https://www.postgresql.org/docs/18/functions-info.html).

A matching recovery-intent receipt is durable before restoring the previous external head. An interrupted repair can be repeated against that identical intent; an already previous head without a prior matching intent is rejected. Receipts are retained, with a hard limit of64 repairs; normal traffic overwrites only the transition slot. Recovery does not reset a run, retry an effect or create cleanup evidence. An explicit current-authority application retry remains necessary after repair.

The process acceptance suite kills a separate TLS server after witness replacement but before commit, observes ordinary operations blocked, obtains PostgreSQL's aborted proof, repairs and repeats the repair, then checks a single report/outbox graph after explicit retry. It separately denies a known committed transition under a temporarily older SQL head. These are bounded trusted-local process-crash semantics. Atomic replace and file fsync do not establish whole-machine power-loss durability, simultaneous custody rollback, cluster restore recency or an automatic disaster-recovery service.
