# Same run and report IDs in two projects

`crossproject_cases.run_cases(ctx)` extends the existing isolated PostgreSQL and TLS campaign after I06–I10 and before checkpoint cutover. It requires the original completed HC1 A import, A’s live sessions and service credentials, the restored A config/policy at version 4, and the shared application factory. It records I30–I32 in the caller's checks only after their assertions pass. Run the cases through the serial campaign owner.

| Group | What the case verifies |
|---|---|
| I30 | A second project registers the same reviewed HC1 A job, proposal and source bytes under a new task, handoff and config/policy version 2. It publishes through four separately enrolled TLS service audiences. A’s matching credentials are denied for B. Both projects then have a completed run with the same run ID, the same report ID, distinct target-bound private packages and exactly one report-ready event per project. |
| I31 | A viewer in each project retrieves its report, export, linked safe source bytes and event stream. Criterion/evidence aliases and source hashes/revisions must resolve. The export identifies its project and current policy. An admin using the same source ID can read the auxiliary fixture in A, while B’s configured allowlist denies it. Secret/taint canaries in plain text, hex and base64 must be absent from the ordinary results. |
| I32 | Two viewer accounts each have membership in exactly one project. For both accounts the raw HTTPS replies for run, report, export, source and SSE reads return HTTP 403 with the single `E_DENIED` error for an existing foreign run, an unknown project and an unknown run in the viewer’s own project. |

The second registration uses the unchanged original source classifications and bytes. The added project context is generated by the versioned execution projection. The fixture’s original executor job and historical assessor response remain pinned to the HC1 review. This campaign performs a new import and publication with historical judgments. It does not execute the historical checks or invoke a new assessor. The ordinary views can be byte-identical when two projects evaluate the same material. Scope is verified by current authorization, export metadata, independent DB associations and project-specific policy decisions.

The module never starts or stops PostgreSQL, a listener or a worker. It creates isolated synthetic records in the caller’s running campaign. Passwords, session credentials, service credentials, grant, effect nonce and lease token are kept out of returned evidence. A completed integration verdict requires an actual owner-controlled campaign with recorded source pins and independent review.
