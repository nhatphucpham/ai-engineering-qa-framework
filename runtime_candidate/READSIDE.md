# Reading and releasing a candidate report

The application calls `read_locked(app, operation, actor, params)` inside its authenticated database unit. The transport enters `release_unit(app, operation, token, body, result)` around each bounded write. That context opens a fresh authenticated unit, recomputes the permitted result, checks the database expiry clock, and holds the shared authority mutex until the write returns. It admits an event page whose buffered records still match the committed prefix if more records have since arrived. For other results, a change to the canonical buffered contents requires a fresh read.

The nine reads use the application operation matrix. A session returns its own user/admin information. Project listing consults current membership, project enablement and the enabled flag on the selected config. Run lists, snapshots and event streams resolve within the selected project. A run read includes the sequence watermark from the same run row as its state and version. Every event sequence in the requested page must exist through that watermark or the 64-row limit. A missing row, unexpectedly empty page below the watermark or cursor ahead returns `E_RESYNC_REQUIRED`. Callers can obtain a new watermark with `run_read`. [Application API](API.md)

## From a criterion to source

1. Request `report_read` for the project and run. Its response contains the core-derived `view`, original `viewSha256`, `reportId`, `sourceLinks` and `sourceLinksSha256`. The view retains criterion results, contextual evidence, reason codes, actions, coverage gaps and pending human decision.
2. Select the `sourceLinks` row whose `criterionId` matches the criterion alias from the view. Each link identifies its role as `requirement`, `obligation`, `comparison`, `evidence`, `check_definition` or `policy`. Requirement claims and comparison contexts carry source positions where available. Only verified AC anchors and in-bounds line ranges of up to 40 lines are exposed. Other historical locator text yields `locatorStatus=unavailable`. Each evidence link carries its own public `evidenceId`. A restricted origin yields its role, `reason=restricted` and the alias when applicable. For the fixed VF1 profile, a separate `check_definition` link uses the held observation, registered test artifact and exact class/method position in its pinned source. The same alias joins this link to the outcome in the view. This identifies the test that generated the observation; comparison links separately preserve the assessorâ€™s chosen scope.
3. For an accessible link, call `source_read` with the same project and run ID and its `artifactId`. The response carries the registered revision, SHA-256, byte length, classification and UTF-8 text, up to 32 KiB of source bytes. Compare the returned revision and digest with the link, then inspect the stated location. Identical artifact IDs in another snapshot resolve only in that snapshot's own scope.
4. Request `report_export` for the same scope. Its response contains the same view, source links and links digest, plus `manifest` and `manifestSha256`. The manifest binds the project, run, report, active config/policy versions and the byte length and SHA-256 of the canonical view and links. JSON responses for reports and exports have a 64 KiB limit and each criterion has up to 64 distinct links. Exceeding either limit returns `E_BUDGET`.

The private report package, stored alias maps, current run-scoped registry rows and actual blob bytes supply the trace. The read checks the private target, held input digests, view and alias map, registered artifact revisions and bytes, and reconstructs the report lineage under the trusted projection profile. Every safe target source must remain allowed by the current configuration. The fixed VF1 profile permits typed outcomes after reconstruction of its specific historical record; the execution and host-request sources themselves remain restricted. Unknown restricted profiles, a missing registry row or a tainted target deny ordinary report release. [Projection scope](PUBLICATION.md)

For executed fixtures, the intake freezes the approved source IDs before a check runs. At publication, the service records a second verified lineage including the execution record and host request from that run’s admitted effect. Reads resolve those two private inputs through the application’s run-scoped `source_record(run, artifact_id)`, verify their exact revision, digest and bytes, and reconstruct the fixed producer profile. The reconstructed lineage must equal the published projection and preserve the originally approved safe source IDs. The original intake remains immutable. Private origins cannot be fetched through `source_read`, even when their IDs appear in a project configuration. The local checks simulate this run-scoped resolver with historical bytes. New execution and durable recovery require separate evidence.

Run `py -3 -B -m unittest -v runtime_candidate.test_readside` from the repo root with the existing candidate dependencies. These checks use a recording store and real historical synthetic bytes. They cover normal criterion-to-source lookup, restricted sources, policy removal, snapshot isolation, changed lists, event gaps and clock expiry. Cross-process authorization and database commit ordering require the separate integrated campaign.
